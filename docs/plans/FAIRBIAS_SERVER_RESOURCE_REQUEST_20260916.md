# FairBias / NHIS 医疗公平性研究服务器资源申请清单

日期：2026-09-16。用途：向导师、课题组负责人或集群管理员申请现有服务器账号与计算配额。以下是基于当前任务的资源规划，未经目标服务器实测，不是采购报价或运行时间承诺。

## 申请建议

优先申请可持续使用的 Linux CPU 计算资源；GPU 作为神经网络方法的补充。建议使用现有课题组服务器或学校计算集群的资源配额。

| 资源 | 推荐申请 | 可接受的较小配置 | 具体用途 |
|---|---|---|---|
| CPU | 32 个可分配 CPU 核，注明物理核或超线程/vCPU | 16 个 CPU 核 | 多方法、参数、随机种子的独立作业并行；初期并发 8–16 个 |
| 内存 | 可用配额 128 GB | 64 GB，降低并发 | 当前单训练任务上限 4 GiB；16 个任务的训练预算合计 64 GiB，额外空间供父进程、缓存和统计分析 |
| 存储 | 200 GB 持久项目空间，SSD 优先；可扩至 500 GB | 100 GB | 环境、官方实现、模型、预测、日志、统计结果和版本快照；并非原始数据本身需要数百 GB |
| GPU（可选） | 可排队使用 1 张显存约 24 GB 的 NVIDIA GPU | 先使用 CPU | 为 TabM、fairret、FRAPPÉ 的设备适配和更充分的神经网络比较留出资源；实际显存需求需短基准确认 |
| 系统 | 受维护的 Linux x86_64；如 Ubuntu 22.04/24.04 或学校既有发行版 | 学校提供的受支持 Linux 环境 | 统一 Python、R、C++ 编译及可选 CUDA 环境 |
| 运行方式 | SSH + Slurm 作业数组或同等批处理机制 | 独立服务器允许受限后台任务 | 断开个人电脑后作业仍可继续；批量调度、资源记账和失败恢复 |
| 使用周期 | 初期 2–4 周，之后按论文进度续用 | 先试用 1 周 | 包含部署、验证、正式实验、统计分析及复现检查，不表示整台机器需独占数周 |
| 配额计费时 | 先申请 500 CPU 核时；GPU 如获分配可先申请 20–50 卡时 | 先给短基准配额再核定 | 这是建议申请额度，包含检查和修复余量，不是实测必需消耗；16 核同时工作 1 小时消耗 16 核时 |

GPU 的用途应与任务分开说明：当前 FairBias、EG+LR/GBDT、LFR、Reweighing、TO、OxonFair 和调查统计路径以 CPU 为主。当前 TabM/fairret 适配器明确使用 CPU，FRAPPÉ 使用单独 TensorFlow 环境；获得 GPU 后仍须实现设备选择并验证数值与复现行为。不能承诺整套 benchmark 获得 GPU 后自动加速。

## 可向导师说明的研究理由

1. **实验规模已经超过方便在个人电脑串行完成的范围。** 当前登记 8,054 个“配置 × 随机种子”任务，包含四个分析方案、多个预测骨干、公平性方法、消融和敏感性分析。部分任务共享表示缓存，并不是 8,054 次同等昂贵的完整训练。
2. **已有实际耗时证据。** 2026-09-16 08:50 的进度检查显示，本地运行约 7 小时 10 分钟后，1,341 个任务结束，其中 1,021 个有效。仅剩余 EG+GBDT 任务，按当前单任务平均时间外推就约需 22 个串行小时；其他方法与最终统计分析尚需额外工作。服务器的主要收益来自跨任务并行和持续运行。
3. **应用论文需要完整、可复核的比较。** 主方法为 FairBias，同时比较预测性能和公平性；除传统对照外，还纳入 FairGBM、FRAPPÉ、fairret 等近期方法及 TabM 预测器。需要执行预定随机种子、参数选择和跨年评估，保留失败记录，避免只展示有利结果。
4. **调查统计也有独立计算工作。** NHIS 抽样权重、分层与 PSU 需要进入设计调整的评价；已登记 2,000 次 PSU 重抽样及配对比较。计算资源支持这些分析，而统计有效性仍由方法与实现验证保证。
5. **稳定运行与可复现环境。** 学校服务器可以提供长期作业、明确资源配额、统一环境和可追踪日志，减少对个人电脑持续开机的依赖，并方便后续论文修订和复现实验。

当前 LFR 的 320 个预算退出来自 40 次原始表示学习失败及其 280 个缓存依赖配置。40 次原始拟合均因函数计算次数限制退出，只进行 3–7 次优化迭代。它暴露出训练预算验证不足，并不意味着内存不足，也不能证明 LFR 的效果较差。服务器提供补做收敛可行性验证的条件，但仍需单独修正并登记预算，保留原始记录。

## 获得账号后的迁移工作

1. 保存当前本地批次和真实运行源码快照。现有实现包含未提交改动，不能仅按旧 Git 提交号重新克隆就视为相同版本。新服务器运行使用独立目录与清单。
2. 重建 Linux 环境。当前 TensorFlow wheel、FairGBM 原生库和 R 库包含 macOS ARM 构建，虚拟环境不能直接复制到 Linux 使用。锁定实际兼容版本并重跑合成、序列化、调查统计对照。
3. 核对 Linux 资源计量。当前 `experiment_worker.py` 直接将 `ru_maxrss` 写为字节；Linux/macOS 的该值单位不同，服务器适配须归一化并验证。作业级内存约束同时使用调度器及独立进程监控。
4. 适配并行调度。当前 `run_nhis_benchmark.py develop` 是串行循环，不能直接启动多个实例共同写同一运行目录。先按表示依赖生成任务图，对共享表示使用单写入者/锁和原子缓存，随后并行下游预测器，防止重复训练及写入冲突。
5. 先维持每任务单计算线程，在相同训练预算下试验 4、8、16 个并发作业，记录吞吐量、峰值内存和失败率，再确定并发上限。神经网络 GPU 作业另列资源与环境。
6. LFR 先做独立的训练端收敛诊断，预算改动必须进入新登记。服务器执行速度差异也应进入计算预算与运行时间比较的解释。
7. 保持相同数据适配、F/C/S 划分、种子和指标。当前方案是 2022 F/C、2023 S、2024 回顾性 T；不得根据 T 的排名改变方法或预算。跨平台结果核验通过后才决定已有产物的复用范围，不直接拼接为同一环境结果。
8. 集中核对所有任务回执和文件哈希后，再进行候选选择、固定模型的 2024 评估和论文表图输出。迁移不会自动授予新的数据传输或付费云资源权限。
