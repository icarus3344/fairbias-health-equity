# 双节点重新分配与剩余时间估计

记录日期：2026-09-17。正式重分配于北京时间 **10:57:53** 启动，核验快照约 **10:59**。

**结果：4090 机器的 CPU 已重新接近满载；两台机器合计 45 个训练进程运行。**

| 节点 | 实际运行进程 | 采样 CPU 用量 | 容器当前内存 | 剩余工作安排 |
|---|---:|---:|---:|---|
| 4090 节点，16 核配额 | 15 个 FRAPPÉ | 15.96 核，约 100% | 36.2 / 80 GiB | 新分配的 100 个任务 |
| 新 CPU 节点，32 核配额 | 30 个 FRAPPÉ | 29.59 核，约 92% | 43.4 / 60 GiB | 原 300 中剩余 115 个，随后自动接另 80 个 |

4090 节点此前 CPU 下降的原因是 LFR 收尾阶段活跃任务变少，但原阶段控制器仍要求全部 LFR 结束后才启动 FRAPPÉ。原机预排 180 个 FRAPPÉ、新机仅承担原 300 的分配，也会使两机收尾时间不均衡。

本次只停止并退休了旧的阶段顺序控制器，保留它的 LFR 训练子进程和原预算。新调度器可以把仍在运行的旧 LFR worker 计入同机 15 个 CPU 槽位，以空余槽位启动 FRAPPÉ。实际开始核验时 LFR 已全部结束，故源机立即进入 15 并发。既有新 CPU 机的 30 个训练进程没有重启。

## 工作划分与去重

完整 480 个 FRAPPÉ 注册任务保持：

- 新 CPU 机原有 300 个任务，继续既有队列。
- 4090 机原预排 180 个中的 100 个，由新队列执行。
- 剩余 80 个转移到新 CPU 机，服务器侧等待原 300 个完成并验证回执后自动启动。

以完整候选的全部 5 个随机种子为分配单位，保留原 seed、参数、训练预算、F/C/S 分区和修复运行时身份。新任务集精确覆盖原 480 个，三部分没有交集；本次实际运行的两机 job 名称也核对无重叠。没有根据公平性或预测性能选择转移任务。

新增 `scripts/run_nhis_balanced_shard.py` 和对应测试。7 个针对分工闭合性、重复/缺失任务、种子拆分、外部负载准入的测试在本地和两台 Linux 主机均通过。两端 70 个原注册源文件 SHA 一致。4090 机 15 个新 worker 已各消耗约 67–71 CPU 秒，证明实际进入计算。

调度进程：原 CPU 主队列 PID `209845`；4090 新队列 PID `479880`；CPU 额外 80 个任务的等待/调度进程 PID `778066`。旧源机阶段控制器 `174423` 已退休，不再执行其过时的 180 个任务阶段。

## 剩余时间

10:59 快照：修复版 FRAPPÉ **185 / 480** 个任务完成，均为 VALID 状态；剩余 **295** 个，其中 45 个在运行。这是状态计数，完整输出验收由随后独立回执核验完成。

新 CPU 节点最近 90 个完成任务的平均用时为 **449.66 秒，即 7.49 分钟**；该窗口观测范围约 **5.88–8.82 分钟**。

- 4090 节点：100 × 7.49 / 15 ≈ **50 分钟**的名义剩余负载。
- CPU 节点：(115 + 80) × 7.49 / 30 ≈ **49 分钟**的名义剩余负载。
- 在途任务已有进展，而最后一批尾部、CPU 两阶段衔接和机器/候选差异会增加不确定性。

因此，**以约 11:00 的快照估计，这轮已经安排的训练队列还需 45–70 分钟，预计 11:45–12:10 收尾**。这是假设没有新失败或额外争用的规划范围，不是统计置信区间；源机新运行时尚未完成首批，暂用新 CPU 实测用时近似，后续必须以真实回执校正。此分配用于接近同时收尾，不声称已经证明全局最短调度。

## “队列完成”与“论文实验完成”的区别

LFR 原注册 **960 个任务已全部终结，全部标为 BUDGET_EXHAUSTED**，其中存在共享表示失败向依赖任务的传播，不能解释为 960 次独立优化都运行到了墙钟超时。

独立抽查一个直接 LFR 拟合，其优化器记录 `funcalls=5805`、`nit=4`、`warnflag=1`，明确报告函数/梯度评估次数超过限制；worker 用时约 332 秒。冻结 adapter 的 `maxiter=5000`、`maxfun=5000`。这是**优化器 maxfun 配额耗尽，不是缺少 CPU 或触发 1,800 秒墙钟预算**。另外两个直接 seed 的同类诊断由子代理核查；本轮主管只将独立核实的一个作为直接实例。

所以，上述约一小时只覆盖当前已排好的队列。LFR 的版本化修复/小规模收敛验证、以及已有 EG、BM、Joint 未关闭问题，不包含在这个 ETA 里；未经验证不承诺这些修复的总耗时。不能把队列结束或进程退出写成所有方法已经能做可靠论文比较。

后续先做运行时一致的结果索引、失败和缺失覆盖表，再开展可比模型的预测、公平性、调查设计不确定性及计算成本分析。旧版 FRAPPÉ 不混入修复版结果。S/T 性能不得用于选择数值修复。
